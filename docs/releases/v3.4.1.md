# Windows PC Toolkit 3.4.1

PC Cleaner 1.4.1: makes the Steam shader-cache row actually cleanable, closes a stale-configuration hole in the VRChat cache row, and finishes the modding-log coverage. Extract the complete **Windows-PC-Toolkit-3.4.1.zip** into a new folder and run **START_TOOLKIT.bat**; close older dashboards first.

## Steam shader cache works again

The cleaner discovered `steamapps\shadercache` under Steam libraries, including the normal `Program Files (x86)` install — and then refused every one of them, because the deletion guard rejects anything under Program Files. The row was advertised and could never run.

- A new **Steam policy** accepts exactly the shadercache folders Steam itself reports, recomputed at delete time from the registry and `libraryfolders.vdf`. Nothing else in Program Files qualifies.
- The Program Files guard is unchanged for every other path: a folder called `Cache`, a `steamapps` folder, `steamapps\common`, `compatdata`, installers and manifests are all still refused.
- Scan and deletion now use the same policy, so a row is advertised as cleanable only when the delete would actually run. The Steam process check and STRICT confirmation still apply.

## VRChat configuration fails closed

The cache row used to accept the scanned location when `config.json` had since been deleted, corrupted, or lost its `cache_directory` — an unprovable state was treated as agreement.

- One resolver now reports the config as `absent`, `default`, `custom` or `invalid`. Only a proven match is fresh.
- A moved custom location, a switch back to the default, a removed config for a custom row, unreadable JSON and unresolvable paths all refuse with "rescan". The documented default still works when no custom path was ever set.
- The scan-time state refuses an unreadable config too, so the row is never shown as cleanable while its location is unknown.

## Modding logs

- **Portable Mod Organizer 2** instances are detected: `logs` directly under the selected root, as well as global instance subfolders.
- A root is accepted only when it proves it is MO2 (`ModOrganizer.exe`, `ModOrganizer.ini` or `nxmhandler.exe`). A folder that merely contains `logs\mo_interface.log` is not authorized.
- MO2, Vortex, DynDOLOD/TexGen/LODGen logs are never deleted while the owning application runs — checked at scan, at clean, and again immediately before each file.
- Skyrim VR checks `sksevr_loader`; Skyrim SE checks its own loader. VR and SE no longer share a process list.

## Catalog

22 categories: 13 deletable, 9 report-only.

Two AI rows were measured and left report-only on purpose. Codex's `cache\codex_app_directory`, `codex_apps_tools` and `remote_plugin_catalog` (about 72 MB on the review machine) and Claude Code's `shell-snapshots` are genuinely regenerable, but both live inside homes the cleaner protects wholesale because sessions, SQLite state, config and secrets share the tree. Deleting them would require weakening that guard for a few megabytes; the rows now measure and explain instead.

## Limits

No live cache, game, modding log or AI home was deleted while validating; every check ran on disposable TEMP fixtures. Sizes are estimates, there is no undo, and shader recompilation, rebuild cost and FPS effects were not measured.

[Validation and runtime limits](https://github.com/SenjuWoo/windows-pc-toolkit/blob/v3.4.1/VALIDATION_REPORT.md). Exact release commit, CI links and hashes are in **release-provenance.json** and **SHA256SUMS.txt**.

Diagnostics: `%LOCALAPPDATA%\WindowsPCToolkit\Logs`. Detailed logging: `-DebugLog` or `WINDOWS_PC_TOOLKIT_DEBUG=1`.
